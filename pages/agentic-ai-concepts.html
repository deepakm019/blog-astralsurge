1. Foundations

A large language model (LLM) takes text in and produces text out. On its own it cannot look up a fact, read your database, or change anything outside the conversation. Three ideas turn it into something more:

  • Context window. Everything the model can see in one call: instructions, conversation history, tool results and retrieved documents. Anything not in the window does not exist for the model in that call.
  • Tool calling. The model can emit a structured request such as search_orders(customer_id="42"). Your code runs the function and returns the result as a new message. The model never executes anything itself.
  • A loop. Your code calls the model again with the new result, repeating until the model returns a final answer instead of a tool request.

An agent is an LLM running in such a loop, where the model decides what to do next. A chatbot answers once. A workflow follows steps you wrote in advance. An agent chooses its own steps while it runs. Most production systems sit between these two, and the rest of this guide shows how to choose the right point on that spectrum.

2. Workflows vs agents

Anthropic's guide Building effective agents draws a useful line. A workflow is a system where LLMs and tools follow predefined code paths. An agent is a system where the LLM dynamically directs its own process and tool use. Workflows are more predictable and cheaper to test. Agents suit open-ended problems where you cannot list the steps in advance.

The common workflow building blocks:

PatternWhat it doesUse it when
Prompt chainingOutput of one LLM call feeds the next, with optional checks in betweenThe task splits cleanly into fixed stages, such as outline, then draft, then translate
RoutingA classifier sends each input to a specialised prompt or modelInputs fall into distinct categories, such as billing, technical or sales questions
ParallelizationIndependent subtasks run at once, or the same task runs several times and results are combinedSubtasks are independent and you want speed, or you want several opinions for confidence
Orchestrator-workersA central LLM breaks the task into pieces at runtime and delegates them to workersYou cannot predict the subtasks in advance, such as editing many files for one change
Evaluator-optimizerOne LLM generates, another critiques, and the loop repeats until the critique passesClear quality criteria exist and iteration measurably improves the result
Rule of thumb: start with the simplest thing that works. A single well-prompted call with retrieval beats an agent for most tasks. Add loops, tools and multiple agents only when a measured failure requires them.

3. Agent types

These names come up constantly. They describe how the loop is organised, not which vendor provides it.

ReAct (reason and act)

The model alternates between a short reasoning step and a tool call, observing each result before deciding the next move. It is the default pattern for tool-using agents and the loop shown in Section 1.

Plan-and-execute

A planner writes the full list of steps first. An executor carries them out, and the plan is revised only when a step fails. This suits long tasks where you want a visible plan before any side effects happen.

Reflection (self-critique)

After producing an answer, the agent reviews its own output against criteria and revises it. The gain depends heavily on whether the critic can actually detect errors. Without a concrete check, reflection tends to rephrase rather than fix.

Router

A single step chooses which specialist handles the request. Simple, cheap and easy to test, and often the right first step before anything more complex.

Supervisor (multi-agent)

One agent receives the request, delegates to specialist agents, and decides when the work is complete. See Section 6.

Hierarchical teams

Supervisors manage other supervisors. Useful when a task has distinct sub-domains, each with its own tools and sub-steps, but it multiplies cost and latency quickly.

Handoff (swarm)

There is no central boss. The active agent transfers control directly to another agent by calling a handoff tool, and the conversation continues with the new agent's instructions and tools.

TypeControlStrengthMain risk
ReActModel, step by stepFlexible, simple to buildWanders or loops without a stop rule
Plan-and-executeUpfront planPredictable, reviewablePlan goes stale when reality differs
ReflectionSelf-review passCatches some errorsCosts double, and may not find real errors

4. Tools and memory

Designing tools

The model chooses tools by reading their names and descriptions, so those descriptions are part of the prompt. Good tools are:

  • Narrow. get_order_status(order_id) beats run_sql(query). Narrow tools are safer and easier to evaluate.
  • Typed. Use a schema for every argument, with enums where values are fixed.
  • Informative on failure. Return "order 4411 not found, check the ID format" rather than a stack trace. The model can recover from the first; it cannot from the second.
  • Least privileged. Read-only by default. Anything that spends money, sends messages or deletes data needs a confirmation step, often a human-in-the-loop interrupt (Section 5).

Kinds of memory

MemoryWhere it livesExample
WorkingThe context window for this runThe current conversation and tool results
Short-term threadA checkpointed state keyed by thread IDResuming a support chat tomorrow
Long-termAn external store, often searched by embeddingRemembering a user's stated preferences across many sessions
ProceduralInstructions and examples in the prompt or codeThe rules for how to write a refund reply
Context is finite and expensive. Summarise or trim old tool output rather than carrying every raw result forward, and keep anything the model must follow near the end of the prompt or in the system instructions.

5. LangGraph

LangGraph is a library from the LangChain team for building agents as explicit graphs. Instead of a hidden loop, you define a shared state, nodes that are functions which read and update that state, and edges that decide which node runs next. The control flow is visible in code, can be drawn as a diagram, and can be paused, saved and resumed.

The four core ideas

  • State. A typed record, usually a TypedDict or Pydantic model, that every node sees. Nodes return only the fields they change.
  • Reducers. Rules for merging updates into state. Annotated[list, add_messages] appends new messages rather than overwriting the list.
  • Nodes. Ordinary Python functions. A node might call an LLM, run a tool, query a database or do plain logic.
  • Edges. Fixed edges always go to the same next node. Conditional edges call a routing function that returns the name of the next node, or END.

A minimal tool-calling agent

from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import ToolNode
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict):
    messages: Annotated[list, add_messages]   # reducer: append, do not overwrite

tools = [search_orders, refund_order]         # plain functions decorated with @tool
llm_with_tools = llm.bind_tools(tools)

def call_model(state: State):
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}           # only the field we changed

def route(state: State):
    last = state["messages"][-1]
    return "tools" if last.tool_calls else END

builder = StateGraph(State)
builder.add_node("agent", call_model)
builder.add_node("tools", ToolNode(tools))    # runs requested tools, returns results
builder.add_edge(START, "agent")
builder.add_conditional_edges("agent", route, ["tools", END])
builder.add_edge("tools", "agent")            # always return to the model after tools

app = builder.compile(checkpointer=MemorySaver())

config = {"configurable": {"thread_id": "customer-42"}}
result = app.invoke({"messages": [("user", "Where is order 4411?")]}, config)

Note the thread_id. With a checkpointer, every call for the same thread continues from the saved state, which is how a chat keeps its history between requests.

Features that matter in practice

  • Checkpointers. Save state after every step. In-memory saving is fine for tests; a database-backed checkpointer is needed for production, so a crash or deploy does not lose a conversation.
  • Human-in-the-loop. Interrupt before a sensitive node, show the proposed action to a person, then resume with their decision. Typical for refunds, deletions and outbound messages.
  • Streaming. Stream tokens, node updates or both, so a UI can show progress instead of a long wait.
  • Subgraphs. A compiled graph can be a node in another graph. Use this to package a research sub-agent with its own state.
  • Send (map-reduce). Dispatch the same node over a dynamic list of inputs in parallel, such as one worker per document, then reduce the results. This is orchestrator-workers from Section 2 expressed in code.
  • Time travel. Load an earlier checkpoint, change the state, and rerun from there. Invaluable for debugging why an agent chose a path.
Why graphs? A hidden loop is easy to start and hard to control. A graph makes every branch, retry and stop condition an explicit line of code you can test, which matters once an agent can spend money or change data.

6. Multi-agent systems

Split one agent into several when specialisation helps: different prompts, different tools, different permissions, or simply a context window that would otherwise fill with irrelevant detail. Splitting for its own sake usually adds cost, latency and coordination bugs.

Common failure modes

  • Agents talking past each other. Two agents redo the same work, or each assumes the other did a step. Fix with a single shared state and explicit ownership of each field.
  • Endless delegation. The supervisor keeps routing back and forth. Fix with a step budget and a stop condition in the graph, not only in the prompt.
  • Context drift. Each hand-off loses details. Pass structured state, not a paraphrase.
  • Cost blow-up. Each agent multiplies the tokens. Measure cost per task in evals before adding a fourth specialist.

7. Evals

An eval is a repeatable test of an LLM system's behaviour. Without one, every prompt change is a guess: it may fix the example you looked at and break three others. Evals turn "it seems better" into a number you can compare.

What to measure

DimensionExample checkHow to score
CorrectnessThe refund amount matches the order recordExact match or code-based assertion
Tool useCalled search_orders before refund_orderCompare the actual tool trajectory with the expected one
GroundednessEvery claim is supported by the retrieved textLLM judge with the source, or a human
Style and policyNo promises of delivery dates; polite toneRubric scored by an LLM judge, spot-checked by humans
Cost and latencyTokens and seconds per taskLogged from traces, compared with a budget
SafetyRefuses a request outside policyPass/fail on adversarial cases

Ways to grade

  • Deterministic code. Regular expressions, JSON schema checks, unit tests on the output. Cheap, fast and reliable, so use them wherever they can express the requirement.
  • Reference-based. Compare with a known good answer, using exact match, token overlap or semantic similarity.
  • LLM-as-judge. A model scores an output against a rubric. Useful for open-ended quality. Validate it: check its agreement with human labels, watch for bias toward longer answers, and pin the judge model and prompt so scores stay comparable.
  • Human review. The ground truth, but slow. Use it to calibrate the automated graders, not to score every run.

Building a dataset that tells you something

  • Start from real traffic. Sample production inputs, especially ones that failed or confused users. Invented examples skew easy.
  • Cover categories deliberately. Common cases, edge cases, adversarial inputs and cases where the right answer is "I don't know".
  • Keep expected outputs at the right level. Often "must cite order 4411 and must not promise a date" is better than one exact sentence.
  • Separate dev and holdout sets. Tune prompts on one set and check the final version on another, or you will overfit the examples you can see.
  • Test agents on trajectories. For agents, check the sequence of tool calls and the final state, not only the final text. A correct answer reached by an unsafe path is still a failure.
Statistics matter. LLM outputs vary between runs. Run each case several times or use a temperature of zero where appropriate, and report pass rates with the number of cases, not a single score. A 2-point change on 20 cases is noise.

Metrics for classic ML and retrieval

Retrieval has its own metrics, covered in the RAG section below: recall at k, precision at k, mean reciprocal rank and normalised discounted cumulative gain (nDCG). These measure the retriever in isolation, which is essential because a generator cannot fix documents it never received.

8. RAG (retrieval-augmented generation)

An LLM knows only what it learned in training, which ends at a fixed date, and it has no access to your private data. RAG adds a retrieval step: find the most relevant passages for the question, place them in the prompt, and ask the model to answer from them. The model gets fresh, specific knowledge without retraining, and you can show the source of each claim.

Stage by stage

1. Chunking

Documents are split into pieces small enough to retrieve precisely but large enough to make sense alone. Common strategies:

  • Fixed size with overlap. Simple and a good baseline. Overlap keeps sentences that straddle a boundary retrievable.
  • Structure-aware. Split on headings, sections or code blocks, and keep the heading path as metadata.
  • Semantic. Split where the topic shifts, detected with embedding similarity between sentences. More expensive, sometimes better.

Attach metadata to every chunk: source, section, date, access permissions. Metadata filters are often the cheapest accuracy gain, for example "only documents from product version 3".

2. Embedding and indexing

An embedding model maps text to a vector so that similar meanings produce nearby vectors. A vector database stores these and finds nearest neighbours quickly. Keep the embedding model and version fixed; changing either means re-embedding everything.

3. Retrieval

  • Dense (semantic) search finds passages that mean the same thing, even with different words.
  • Sparse (keyword) search, typically BM25, finds exact terms such as error codes, product names and identifiers, which embeddings can blur.
  • Hybrid search runs both and merges the ranked lists, often with reciprocal rank fusion. This is the sensible default for real corpora.
  • Query rewriting lets the model turn a vague follow-up into a standalone search query, using the conversation so far.

4. Reranking

Retrieval is tuned for recall, so it returns many candidates. A cross-encoder reranker reads the question and each candidate together and scores them more accurately. Retrieve around 50 candidates cheaply, rerank, then keep the top 5 or so for the prompt.

5. Generation with grounding

The prompt should instruct the model to answer only from the supplied context, to say when the answer is not there, and to cite chunk IDs. Number the chunks so the citations can be checked and linked back to the source.

A minimal, provider-neutral sketch 
def answer(question: str) -> dict:
    q_vec = embed(question)                       # same model as ingestion
    candidates = hybrid_search(question, q_vec, k=50, filters={"product": "v3"})
    top = rerank(question, candidates)[:5]        # cross-encoder scores
    context = "\n\n".join(f"[{i+1}] ({c.source}) {c.text}" for i, c in enumerate(top))
    prompt = (
        "Answer using only the numbered sources. Cite them like [1]. "
        "If the sources do not contain the answer, say so.\n\n"
        f"Sources:\n{context}\n\nQuestion: {question}"
    )
    return {"answer": llm(prompt), "sources": [c.source for c in top]}

Evaluating RAG

Split the evaluation in two, because the failures are different:

LayerQuestion it answersTypical metrics
RetrievalDid the right chunks come back?Recall at k, precision at k, MRR, nDCG, using labelled relevant documents
ContextIs the retrieved text relevant and free of noise?Context precision, context relevance (judge-scored)
FaithfulnessDoes the answer stick to the context?Claim-level support check against the retrieved text
Answer qualityDoes the answer actually address the question?Answer relevance, correctness against reference answers

A common mistake is to tune the prompt while the real problem is retrieval. If recall at k is low, no generator will fix the answer. Measure retrieval first.

Common failure modes

  • Chunks too small lose the context that makes them meaningful. Chunks too large dilute the signal and waste the context window.
  • Stale index. Documents changed but embeddings did not. Track document versions and re-ingest on change.
  • Missing answers. The information is split across chunks. Try parent-document retrieval, where small chunks are matched and the larger section is passed to the model.
  • Hallucinated citations. The model cites [4] when only three sources exist. Validate citation IDs in code.
  • Prompt injection in documents. Retrieved text can contain instructions. Treat it as data, keep system instructions separate, and limit what tools the answering step can use.

Beyond basic RAG

  • Agentic RAG. The agent decides whether to retrieve, what query to send, and whether the results were enough, possibly retrieving again. In LangGraph this is a retrieval tool inside the agent loop from Section 5.
  • Multi-hop retrieval. Answering one question needs facts from several documents in sequence. Each step's result shapes the next query.
  • GraphRAG. Build a knowledge graph of entities and relations from the corpus, then retrieve connected subgraphs. Helpful for "what themes run across these reports" questions that keyword and vector search handle poorly.
  • Long context instead of RAG. A large context window can hold a small corpus whole. It is simpler, but costs more per request, and quality can drop when relevant text is buried in the middle. Measure before choosing.

9. Putting it together

A practical sequence for a new agentic feature:

  1. Define the task and failure cost. What must never go wrong? That decides how much autonomy and how many human checks you need.
  2. Write 30 to 50 eval cases from real or realistic inputs before building anything complicated.
  3. Start with a single call. Add retrieval if the answer depends on private or changing data. Measure retrieval recall separately.
  4. Add a workflow (routing, chaining or parallel calls) where the steps are known.
  5. Add an agent loop only for the steps that genuinely need the model to choose its path. Put a step budget and a stop condition in the graph.
  6. Add checkpoints and interrupts before any action with real-world effects.
  7. Gate releases on evals and log traces in production so new failures become new test cases.

10. Glossary

TermMeaning
AgentAn LLM in a loop that chooses its own next action, usually with tools
ChunkA piece of a document stored and retrieved as one unit in RAG
CheckpointerComponent that saves graph state so a run can resume or be inspected
Conditional edgeA graph edge chosen at runtime by a routing function
EmbeddingA vector that represents the meaning of a piece of text
EvalA repeatable test that scores an LLM system's behaviour
Golden datasetA curated set of inputs with expected results or criteria, used for evals
GroundingBasing an answer on supplied sources and citing them
HallucinationA fluent output that is not supported by the context or facts
Human-in-the-loopA pause where a person approves, edits or rejects an agent's next action
LLM-as-judgeUsing a model to score another model's output against a rubric
NodeA step in a LangGraph graph: a function that reads and updates state
ReducerA rule for merging a node's update into the existing state
RerankerA model that re-scores retrieved candidates more accurately
TraceA recorded log of an agent run: prompts, tool calls, results and timings
Vector indexA data structure for fast nearest-neighbour search over embeddings
